# 舌诊功能文档

## 1. 功能概述

舌诊模块用于采集用户舌象图片，并通过 AI 视觉模型完成舌象结构化分析，最终输出：

- 初步辨证结论
- 五项舌诊量化指标
- 雷达图可视化结果
- 置信度说明

当前实现已经从本地 YOLO 检测迁移为多模态大模型识别，核心目标是保留原有的业务接口和报告流程，同时让分析能力更贴近真实的中医舌诊场景。

---

## 2. 整体流程

1. 前端在 [Vue/zhongyi/src/views/Detect/Wang.vue](../Vue/zhongyi/src/views/Detect/Wang.vue) 中打开摄像头或上传图片。
2. 图片以 `FormData` 形式提交到 Java 后端的望诊接口。
3. Java 后端在 [demo/src/main/java/com/tx/demo/controller/WangController.java](../demo/src/main/java/com/tx/demo/controller/WangController.java) 中接收图片、调用 Python AI 服务，并整理返回结果。
4. Python 服务在 [tcm-ai-service/core/tongue_shizhen.py](../tcm-ai-service/core/tongue_shizhen.py) 中完成图像预处理、大模型调用、结果解析和雷达图生成。
5. 前端展示结论、置信度、雷达图和采集样本，并可继续下一个诊断或生成报告。

## 3. 文件作用说明

### 3.1 前端页面

#### [Vue/zhongyi/src/views/Detect/Wang.vue](../Vue/zhongyi/src/views/Detect/Wang.vue)

这个文件是舌诊的前端采集与结果展示页，主要职责是：

- 打开摄像头并拍照
- 处理本地图片上传
- 将舌象图片提交到后端
- 展示分析完成后的结果卡片
- 显示雷达图、模型置信度和初步辨证结论
- 提供“重新分析 / 继续下一个诊断 / 生成报告”入口

它不负责真正的 AI 判断，只负责采集、发送和展示。

#### [Vue/zhongyi/src/constants/algorithmReferences.js](../Vue/zhongyi/src/constants/algorithmReferences.js)

这个文件维护各诊断模块的参考文献数据。

- `wang.references`：舌诊页面底部“参考文献与出处”对应的数据源
- 作用是让页面显示更贴近当前实现的技术说明
- 舌诊部分应体现“视觉大模型 + 舌诊分析”的来源，而不是旧的 YOLO 检测说明

#### [Vue/zhongyi/src/utils/reportUtils.js](../Vue/zhongyi/src/utils/reportUtils.js)

这个文件负责报告跳转和报告生成相关的通用工具方法。

- 负责把当前患者、身份证号、已完成诊断类型等参数带到报告页
- 用于舌诊完成后直接生成当前板块报告
- 避免各诊断页面重复写跳转逻辑

---

### 3.2 Java 后端

#### [demo/src/main/java/com/tx/demo/controller/WangController.java](../demo/src/main/java/com/tx/demo/controller/WangController.java)

这是舌诊接口的 Java 网关控制器，主要职责是：

- 接收前端上传的舌象图片
- 保存图片到本地或业务目录
- 调用 Python AI 服务
- 解析 AI 返回结果
- 将结果写入诊断记录
- 返回前端需要展示的数据

这个文件是前端和 AI 服务之间的桥梁，不直接做图像识别。

它目前会把以下字段返回给前端：

- `main_result`：初步辨证结论
- `chart_img`：雷达图 base64 图片
- `confidence`：模型置信度
- `scores`：五项舌诊分值
- `details`：如果有补充结构化解释，会一并返回

#### [demo/src/main/java/com/tx/demo/entity/Diagnosis.java](../demo/src/main/java/com/tx/demo/entity/Diagnosis.java)

这个实体类用于保存诊断数据。

- 存储舌诊结果、图片地址、置信度、分值等内容
- 为报告生成和历史记录查询提供数据基础

#### [demo/src/main/java/com/tx/demo/controller/ReportController.java](../demo/src/main/java/com/tx/demo/controller/ReportController.java)

这个文件负责综合报告生成。

- 汇总舌诊、闻诊、问诊、切诊等多个诊断板块
- 根据已完成板块生成单板块报告或部分报告
- 舌诊结果会被纳入整体报告内容中

### 3.3 Python AI 服务

#### [tcm-ai-service/core/tongue_shizhen.py](../tcm-ai-service/core/tongue_shizhen.py)

这是舌诊 AI 分析的核心文件。

主要职责：

- 对输入图片进行基础质量检查
- 将图片转为 base64
- 调用 Qwen 视觉模型进行识别
- 要求模型输出严格 JSON
- 解析 `main_result`、`confidence`、`scores`
- 调用雷达图生成器输出可视化结果

它是当前舌诊“智能判断”的真正核心。

这里的五个分值分别对应：

- 舌色偏红指数
- 舌色偏淡指数
- 苔色黄腻指数
- 瘀血征象指数
- 津液亏虚指数

#### [tcm-ai-service/core/image_processor.py](../tcm-ai-service/core/image_processor.py)

这个文件负责图片基础预处理和质量判断。

它的作用不是“识别疾病”，而是做输入质量控制，例如：

- 判断图片是否过暗
- 判断图片是否过模糊
- 给出是否适合送入大模型的初步结论

它的意义在于减少无效请求，避免明显不清晰的图片直接进入大模型，降低误判和浪费。

#### [tcm-ai-service/core/visualizer.py](../tcm-ai-service/core/visualizer.py)

这个文件负责生成雷达图。

- 根据五项舌诊分值绘制结构化图谱
- 在图中展示分区背景、数值标注、置信度说明
- 返回 base64 图片供前端直接显示

它只负责可视化，不负责医学判断。

#### [tcm-ai-service/api/router_sound.py](../tcm-ai-service/api/router_sound.py)

这个文件是闻诊接口，不属于舌诊主逻辑，但它和舌诊一样都属于四诊模块，接口风格和返回结构有参考价值。

#### [tcm-ai-service/main.py](../tcm-ai-service/main.py)

Python 服务入口文件。

- 启动 FastAPI 应用
- 注册路由
- 对外提供舌诊 API

## 4. 舌诊接口返回字段

舌诊分析成功后，前端通常会拿到如下结构：

```json
{
  "success": true,
  "data": {
    "main_result": "初步辨证结论",
    "chart_img": "data:image/png;base64,...",
    "confidence": 0.75,
    "scores": {
      "舌色偏红指数": { "mean": 35, "std": 0 },
      "舌色偏淡指数": { "mean": 20, "std": 0 },
      "苔色黄腻指数": { "mean": 60, "std": 0 },
      "瘀血征象指数": { "mean": 15, "std": 0 },
      "津液亏虚指数": { "mean": 25, "std": 0 }
    },
    "details": {}
  }
}
```

前端的结果页会根据这些字段展示：

- 置信度标签
- 雷达图
- 五项指标进度条
- 初步辨证结论
- 模型解读要点

## 5. 底层文件传递链路

这一部分是理解整个舌诊模块最关键的内容。舌诊不是“前端直接把图片传给大模型”，而是经过了三段传递：

1. 前端把图片封装成表单文件上传到 Java
2. Java 把图片保存成本地临时文件，再转发给 Python
3. Python 读取文件并转换成模型可消费的图像输入，最后把结果再返回给 Java 和前端

### 5.1 前端：把图片变成上传文件

位置： [Vue/zhongyi/src/views/Detect/Wang.vue](../Vue/zhongyi/src/views/Detect/Wang.vue)

前端拿到的原始图片有两种来源：

- 摄像头拍照后生成的 base64 字符串
- 用户从本地相册选择的图片文件

在 `uploadImage(base64)` 中，前端会先把 base64 转成 Blob，再组装成 `FormData`：

```text
base64 图片
→ fetch(base64).blob()
→ new FormData()
→ formData.append('file', blob, 'tongue.jpg')
```

这里的关键点是：

- 前端并没有直接发 JSON 图片字符串给后端
- 它发的是标准的 `multipart/form-data`
- 图片字段名固定叫 `file`
- 另外还会一起带上病人 ID、身份证号、诊断会话 ID

也就是说，前端送到后端的不是“显示用图片”，而是一个真正的上传文件对象。

### 5.2 Java：先接收文件，再保存成临时文件

位置： [demo/src/main/java/com/tx/demo/controller/WangController.java](../demo/src/main/java/com/tx/demo/controller/WangController.java)

Java 端的方法签名是：

```text
handleWang(Patient patient, MultipartFile file, Long diagnosisId)
```

这里的 `MultipartFile file` 就是前端上传的那张图。Spring Boot 会自动把 `FormData` 里的 `file` 字段映射成这个对象。

Java 收到以后会做两件事：

1. 把文件保存到本地临时目录 `E:/项目/zhongyi_uploads/tcm_temp/`
2. 再用 `FileSystemResource` 包装这个临时文件，转发给 Python 服务

关键过程如下：

```text
MultipartFile
→ file.transferTo(destFile)
→ FileSystemResource(destFile)
→ RestTemplate.postForObject(...)
```

为什么要先落盘？

- 便于排查问题，服务端可以直接看到原始上传文件
- Python 端使用本地文件读取更稳定
- 避免内存中反复传递大图片数据
- 方便后续做审计、重试和日志追踪

### 5.3 Java 转发给 Python：再次用 multipart 上传

Java 并不是把图片内容手动拼成字符串，而是再次组装了一个 multipart 请求：

```text
MultiValueMap<String, Object> body = new LinkedMultiValueMap<>()
body.add('file', new FileSystemResource(destFile))
restTemplate.postForObject(pythonUrl, requestEntity, String.class)
```

这里的含义是：

- Java 端对 Python 来说也是一个“上传文件的客户端”
- Python 接口收到的也是一个 `file` 文件字段
- 这样前后端和 AI 服务之间的数据结构保持一致

### 5.4 Python：接收文件后做图像解码和 AI 分析

位置： [tcm-ai-service/core/tongue_shizhen.py](../tcm-ai-service/core/tongue_shizhen.py)

Python 服务拿到文件后，通常先做基础质量判断，再进入模型识别。

文件在 Python 内部的处理路径大致是：

```text
上传文件
→ 读取字节流
→ OpenCV 解码成图像矩阵
→ 图像预处理
→ base64 编码
→ 发送给视觉大模型
→ 解析 JSON 结果
→ 生成雷达图
```

这里最重要的两步是：

- `cv2.imencode(...)`：把图像再转成模型调用需要的格式
- `json.loads(...)`：把模型输出解析回结构化结果

Python 不直接返回一张原图，而是返回：

- 结论文本
- 置信度
- 五项分值
- 雷达图 base64

### 5.5 返回给前端：结果不是文件，而是结构化 JSON

最后 Python 的结果会经过 Java 再返回前端。前端收到的是一个 JSON 响应，不是文件本身。

最终前端拿到的数据一般是：

```text
main_result
chart_img
confidence
scores
details
```

前端再把其中的 `chart_img` 当作图片地址展示，把 `scores` 渲染为进度条，把 `confidence` 转成百分比显示。

### 5.6 一条完整的数据链路

可以把整个过程理解成：

```text
Wang.vue
  → 组装 FormData(file + patientId + idCard + diagnosisId)
  → WangController
    → MultipartFile 落盘成临时文件
    → RestTemplate 转发给 Python
      → tongue_shizhen.py
        → OpenCV 处理
        → Qwen 视觉模型分析
        → 生成 JSON + 雷达图
      ← Python 返回结果
    ← Java 解析并补充字段
  ← 前端渲染结果页
```

## 6. 设计原则

1. 保留原有接口，不破坏后续报告和历史记录逻辑。
2. 以多模态大模型为核心，不再依赖旧的 YOLO 舌象检测流程。
3. 预处理只做质量控制，不承担最终诊断职责。
4. 页面展示优先突出模型结果，其次才是采集图和说明文字。
