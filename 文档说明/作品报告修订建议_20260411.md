## 3. 按章节逐条修改建议

### 3.0 先单独修订：四诊合参报告模块（重点中的重点）
你这块确实不是“调用一次LLM”这么简单，建议在正文里把它写成一个完整的多阶段管线，而不是一句“合参生成报告”。

建议在第4章单独强调以下 7 个技术层：
1. 会话层：诊断会话 caseId 机制，保证同一次就诊四诊结果聚合在同一记录。
2. 数据聚合层：ReportController 在生成报告前先做 patientId/idCard 补齐，再按 caseId 或当日记录解析诊断。
3. 完成度判定层：已从“必须四诊完成”改为“至少1个板块完成可生成”。
4. 结构化上下文层：后端会把四诊结构数据、问卷体质画像、切诊质量分级、字段词典 llmContext 一并传给AI。
5. 策略控制层：前端可配置 focusMode 与 customPromptTemplate，控制“平衡分析”或“单板块深挖”。
6. 传输协议层：新增流式接口 `/api/report/generate/stream`，前端按 SSE 增量渲染，支持取消与中断恢复。
7. 兜底层：DeepSeek 不可用时，Python synthesis 自动退化为规则引擎文本，保证服务连续性。

建议你在正文中明确：
- 这是“前端策略控制 + Java中台聚合 + Python提示词编排 + 流式协议输出”的协同系统。
- 合参结果不是单轮文本拼接，而是多源结构化数据驱动的诊断生成流程。

### 3.0.2 四诊合参板块建议替换为“端到端流程说明”
建议在原“4.2.5 综合诊断模块”里加入下面这个流程文本（可直接粘贴）：

1. 前端在诊断中心汇总已完成板块，携带 `patientId/caseId/completedTypes/focusMode/customPromptTemplate` 进入报告页。
2. 报告页优先请求诊断快照接口，若无 synthesis 则触发流式生成接口。
3. Java 报告控制器解析患者身份与会话，校验至少一个板块完成后，构建四诊结构化输入：
	- 望诊：result + tongueMetrics
	- 闻诊音频：conclusion + confidence + tags + features
	- 问诊：conclusion + scores + constitutionProfile
	- 切诊：HR/SpO2/validRate/sampleCount + qualityLevel/band + keyMetrics(条件注入)
4. Java 将结构化输入转发至 Python synthesis 服务，非流式和流式共用同一提示词框架。
5. Python 按 focusMode 生成不同篇幅策略，并融合自定义提示词与字段说明上下文，输出 Markdown。
6. 前端增量接收 `meta` 与 `content`，实时渲染报告正文，支持用户中途取消。
7. 当 AI 服务异常时自动切换 fallback 文本策略，保证报告页面可用。

### 3.0.3 四诊合参板块的“实事求是写法”
为了避免答辩时被追问，建议你在文中加两句边界说明：
1. `completedTypes` 当前不仅用于页面完成度与策略提示，也用于引导报告生成意图；实际纳入分析的数据仍以诊断记录中的有效字段为准。
2. 切诊 `keyMetrics` 在侧重切诊模式下会优先进入深度分析，平衡模式下以核心指标为主。

综合诊断模块是系统的多服务协同中枢，不再是单一接口拼接文本。模块以诊断会话为主线，将望、闻（音频）、问、切的结构化结果进行统一聚合，支持在完成任意板块后生成阶段性报告，并随诊断进展动态升级报告完整度。系统前端支持配置分析侧重模式与自定义提示词；后端在生成前进行患者身份补齐、会话解析和完成度校验，随后构建包含四诊数据、体质画像、切诊质量分级与字段语义上下文的标准输入，转发至AI合参服务。AI服务按策略生成Markdown报告，并通过流式协议将内容增量回传前端，实现“边生成边展示”的交互体验；当大模型服务不可用时，自动退化到规则引擎输出基础建议，保证系统连续可用。该模块体现了“业务流程控制、结构化数据治理、提示词工程与实时交互协议”四位一体的工程化能力。
